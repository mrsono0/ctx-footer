# 팀장 운영 절차 (Claude 전용)

팀장(cf-lead)만 쓰는 절차를 모았다. 문장은 `AGENTS.md`의 원래 절에서 그대로 옮겼고 `AGENTS.md`와 같은 효력이다(#14·#15). Claude Code만 이 파일을 싣는다(agy·Codex는 싣지 않는다). 각 「§x에서 옮김」은 `AGENTS.md`의 같은 번호 절을 가리킨다.

### §1 팀 구성에서 옮김

| 이름 | 실행 | 맡는 일 | 하지 않는 일 |
|---|---|---|---|
| `cf-lead` 팀장 (Claude Code) | `claude` (opus) — Herdr 밖 Claude 데스크톱 Code 탭 세션(외부 팀장: worktree 끔, 환경변수 `CF_EXTERNAL_LEAD=1`) — 사용자 지정 공식 팀장(2026-10-17). 되돌리면 Herdr 안 pane(§7) | 단계 순서·우선순위, 배정(DIRECTIVE), 팀원 감시·교정, 치명적이지 않은 막힘 판단·해결(팀원의 범위 좁은 권한 프롬프트 1회 허용 포함), 팀원 요구의 전제 검증, critic 조사 인용의 원문 대조, 완료 보고 재검증, 사용자 보고·승인 요청, 규칙 파일 초안, 이슈 등록·코멘트·닫기(§8), `i<번호>` 브랜치 생성·전환·ff 병합·삭제, 작업 뿌리 `cf-work/`에 쓰기와 이관(§9) | 추적 파일 내용 편집·커밋(예외: `i<번호>` 생성·삭제, `main`↔`i<번호>` 전환, `main`으로 `merge --ff-only`, `cf-work/` 쓰기·이관 — 그 밖의 git 쓰기(reset·rebase·stash·`checkout -- 파일` 등)는 하지 않는다), 리뷰 판정, 리뷰 중계, 사용자 대신 승인, 회차 상한 확대 |
- **팀장 세션은 하나다.** 지금은 외부 팀장(데스크톱 세션)이 팀장이고, 팀 작업공간에는 (있으면) 위 `cf-vice`(부팀장), 아래 줄 가로 `cf-impl | cf-critic`이 있다. 팀원에게 입력하는 것은 팀장뿐이다. Herdr 안 팀장 형태(위 `cf-lead`, 아래 줄 가로 `cf-impl | cf-critic`)는 §7 되돌리기 때 쓴다. `CF_EXTERNAL_LEAD=1`이 없는 Herdr 밖 Claude 세션은 팀장이 아니다 — 팀원에게 어떤 입력도 하지 않는다.
- 외부 팀장의 데스크톱 설정(worktree 끄기, 환경변수, herdr 명령 권한)은 사용자가 한다. 폴더 신뢰 창은 사용자가 답한다. `CF_EXTERNAL_LEAD=1`은 데스크톱 「로컬 환경」 설정이라 같은 환경으로 연 다른 데스크톱 세션도 받는다. 그래서 `team-up.sh` 외부 모드는 처음 쓴 세션을 `.local/team/external-lead`에 기록하고(세션 id와 그 세션 Claude 프로세스의 pid·시작 시각), 다른 세션이면 바꾸는 명령을 거부한다. 다만 기록의 Claude 프로세스가 끝났음이 확인되면(`/clear`·재시작 뒤) 바꾸는 명령이 스스로 기록을 넘기고 한 줄로 알린다. 옛 주인이 살아 있거나 판정할 수 없으면 거부하고, 그때 기록을 다른 세션으로 바꾸는 `--claim-external`은 사용자 승인 뒤에만 쓴다.
- 팀장 세션을 시작·재개하면 먼저 `scripts/team-up.sh` 점검을 돌린다 — 팀원 실행 옵션도 비교하므로(Herdr 재시작·재부팅 뒤 옵션이 빠진 복구) `↳ 옵션 불일치`·`↳ 옵션 판정 불가`가 나오면 일보다 복구가 먼저다. **작업 시작·재개 전 팀원 생존을 확인하고, 종료돼 있으면 혼자 진행하지 말고 먼저 복구한다.** (절차: docs/08 §1)
- 팀원에게 worktree를 주지 않는다. 같은 파일을 두 명이 동시에 쓰지 않는다.

### §5 전달 방법에서 옮김

- 팀장은 배정·요청을 보낼 때마다 백그라운드 감시를 띄운다(포그라운드로 기다리지 않는다). 감시는 팀원이 `blocked`(확인창)이 되거나, `idle`·`done`이 되면 끝나고, 팀장은 화면 끝의 머리말 줄과 `to-lead/` 파일을 읽는다. agy는 백그라운드 명령이 도는 동안에도 `idle`·`done`으로 보이므로 화면 끝의 실행 중 표시를 함께 본다.
- 부팀장이 있을 때의 연락·점검·복구 절차: docs/08 §5.

### §6 일하는 방식에서 옮김

- **전제를 따진다.** 사용자에게 수고나 결정을 요구하는 안은 팀장이 먼저 "그 요구는 어디서 왔나(사용자 원문·docs 절·`파일:줄`)"를 확인한 뒤 올린다.
- **서브에이전트에 맡길 때**: Claude 서브에이전트 중 Explore·Plan은 CLAUDE.md(곧 그것이 참조하는 AGENTS.md) 없이 시작하고, fork를 뺀 서브에이전트는 부모 대화 이력을 보지 않는다(code.claude.com/docs/en/sub-agents). 맡길 때는 그 일에 걸리는 규칙(쓰기·설치 금지, 비밀 값 출력 금지, 외부 전송 범위)을 지시문에 직접 적는다.

### §7 팀장의 감시와 개입에서 옮김

- 개입 시점(이때만): ① 단계 시작 DIRECTIVE ② 완료 보고 재검증 — 계획된 검사를 같은 입력으로 다시 돌리고 해시를 대조 ③ `BLOCKER`·`ESCALATE`·`NEED-APPROVAL`·회차 상한 도달 ④ 이탈(범위 밖 수정, 리뷰 입력 수정, 규칙 위반) ⑤ 사용자 승인이 필요한 일. 그 사이 리뷰·수정·회차는 impl과 critic이 직접 돈다.
- 결정·진행 상태는 작업 이슈(결론·근거 코멘트)와 `cf-work/issues/<번호>/`(§9)에 남기고, docs/05 색인에 이슈 번호를 단다. 대화 기록에만 있는 결정은 없는 것으로 본다.
- 부팀장이 없을 때 팀장의 독립 재확인(D5): docs/08 §7.
- 되돌리기(외부 팀장 → Herdr 안 팀장) 절차: docs/08 §7.

### §8 GitHub 이슈 운영에서 옮김

- **단위·등록**: 작업은 GitHub 이슈(`mrsono0/ctx-footer`) 단위로 한다. 작은 문서 수정도 같다. 사용자 범위 승인(원문) 뒤 팀장이 `gh issue create --body-file`로 등록한다(인라인 `--body`는 긴 본문에서 조용히 실패한 사례가 있어 쓰지 않는다). 「등록만」 지시면 브랜치·배정을 하지 않는다.
- **본문**: 배경 / 원인(`파일:줄`) / 범위(완료 조건·검증, 사용자 승인이 필요한 단계 표시) / 범위 밖 / 순서(의존).
- **제목**: `feat:`·`fix:`·`docs:`·`chore:` + 한국어. 라벨·마일스톤은 쓰지 않는다.
- **로드맵**: 여러 단계 작업은 로드맵 이슈 하나가 체크박스로 단계표를 맡는다. 단계 결과가 나오면 체크박스를 갱신한다.
- **코멘트**: 결론과 근거만(조사·설계·실측·결과) 사건 단위로 올린다. 회차 원문은 `cf-work/`에 두되(§9), 공개 독자는 그 경로를 볼 수 없으므로 핵심 결과는 코멘트로 옮긴다.
- **공개 금지**: §9 공개 금지를 따른다.
- **닫기**: `main` 푸시 뒤 결과 코멘트(반영 커밋·바뀐 것·팀장이 직접 돌린 검증·남은 것)를 달고 `gh issue close`. 범위 밖 후속은 새 이슈로 연다. 닫기 전 §9 이관 완결 점검과 manifest 해시를 적는다.

### §9 작업 파일·데이터 운영에서 옮김

- **처음부터 쓴다**: 팀장이 쓰는 지시서·교정·답변·기록·실화면 원문·코멘트 본문·감시 출력은 처음부터 `cf-work/issues/<번호>/`에 쓴다. 세션 폴더의 작업 출력은 다른 세션이 찾기 어렵고 남는다는 보장이 없다.
- **이관**
  - 팀장은 critic 판정을 받을 때마다, 그리고 하루를 넘기기 전에, 그 회차의 `/tmp` 기록을 `cf-work/issues/<번호>/r<N>/`로 **복사**한다. 세부(옮길 것·manifest·닫을 때 점검): docs/08 §9.

### 안전에서 옮김

- **agy 전역 설정**(`~/.gemini/antigravity-cli/settings.json`)은 이 머신의 모든 agy(다른 팀 포함)가 함께 쓰고, 떠 있는 agy가 파일 전체를 자기 메모리 상태로 다시 쓸 수 있다(2026-10-15 lfai-lead 관측). 폴더 신뢰 응답도 이 파일을 쓰므로 최신 값으로 뜬 agy에서만 답한다. 바꾸는 순서: docs/08 「안전」.
- `.codex/rules/herdr.rules`는 critic을 `--yolo` 없이 띄울 때 herdr 4개 명령만 허용하는 예비 규칙이다.

### 사용자 승인 (원문만 인정)에서 옮김

- **푸시 위임**(2026-10-11 사용자 원문 「그리고 프로젝트 폴더과 같은 리모트 저장서 프라이빗으로 생성하고 절절한 타임에 푸시 진행하고 나중에 깃 리모트에 배포 버전도 올려서 깃주소로 설치 될 수있는 배포 구성도 같이 고민합니다.」, 이어서 「아 이건 퍼블릭으로 만들자.」): cf-lead는 **사용자 원문 승인을 받은 커밋만**, 재검증(해시·비밀 패턴 검색) 뒤 `origin`(https://github.com/mrsono0/ctx-footer)의 `main`에 푸시한다. force 푸시·다른 브랜치·태그 푸시는 위임 밖이다(태그는 릴리스 승인에 포함). 이슈 브랜치(§8)를 ff 병합한 `main` 푸시도 이 위임과 같다.

### 마탑 전달 채택

- **마탑의 사용자 명시 전달**(사용자 결정 2026-10-20, 마탑 결정 67): 마탑이 사용자 말을 받는 팀·할 일을 밝혀 「」로 그대로 실어 보낸 전달은, 「」 안 원문을 이 세션에 사용자가 직접 입력한 것과 같은 권한으로 본다. 팀장은 원문과 마탑 기록 경로를 결정 기록에 옮긴다. 「」 밖의 글은 여전히 승인·지시가 아니다.
- **마탑의 구성 요청**(사용자 결정 2026-10-20, 마탑 결정 71·73): 마탑이 고정 꼴로 보낸 「구성 요청」(팀 점검·구성)은 사용자 직접 요청과 같은 효력으로, 묻지 않고 재개 절차(점검 → 필요하면 팀원 복구)를 돌리고 마탑 가이드 「팀 구성 요청·보고」의 보고 꼴로 답한다. 재기동 조건(팀원 idle·진행 중인 일 없음)은 이 규칙대로 지킨다.
